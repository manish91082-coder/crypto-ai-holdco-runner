## 1. Decision summary

The OCI public-GUA IPv6 + Internet Gateway → Neon Data API HTTPS path remains the leading *conditional* network hypothesis. It is not approved or proven. This review adds four material findings:

1. **OCI Budgets are not a hard spend barrier.** Oracle calls budgets "soft limits" and evaluates alert rules periodically every 24 hours. They notify; they do not themselves stop a resource or prevent an overage. A budget alert must never be treated as proof of zero spend.
2. **An un-upgraded Free Tier account is materially different from a Pay-As-You-Go account.** Oracle says Always Free resources remain available after a standard Free Trial expires, paid resources are reclaimed when the account is not upgraded, and the card is not charged unless the account is upgraded (subject to identity-verification authorization holds and special Free Trial offer exceptions). This gives a conditional zero-charge route only if the existing account is demonstrably Free Tier / Always-Free-only and remains un-upgraded. The user's account state is UNKNOWN.
3. **OCI can express IPv6 destination CIDR rules.** Its security lists and NSGs support IPv6; the Internet Resolver supports resolution of external IPv6 hostnames. This makes a narrow egress rule technically possible if the exact Neon Data API AAAA set is stable. It does not prove that Neon Data API has AAAA, that the addresses are stable, or that the rule set can be maintained safely without broad permissions.
4. **Neon Function environment variables are deployment snapshots, not a proven HSM-equivalent key vault.** Current Neon docs confirm that each deployment carries a snapshot of user-defined variables and that the Data API URL is injected branch-locally when provisioned. Reviewed docs do not specify the field-level confidentiality boundary, operator-access model, snapshot retention/deletion semantics, or audit trail for private signing keys stored in those snapshots. The secret-vault gate remains BLOCKED.

**Go/no-go:** NO-GO for OCI provisioning, Neon child-branch creation, Data API activation, key creation, or runtime deployment. P03.03 remains PARTIAL; Quota Governor remains `PAUSE_DEGRADED` / `work_allowed=false`.

## 3. OCI cost boundary

### 3.1 What Oracle documents

- Oracle states there is no charge for creating or using VCNs; other OCI services and data transfer remain subject to published charges.
- Oracle's public networking pricing states the first 10 TB/month of public internet egress is free globally. Usage above the allowance can be chargeable.
- Oracle Free Tier includes Always Free services with unlimited duration, subject to service limits. It also includes a time-limited Free Trial credit offer.
- Oracle's Free Tier FAQ states card details are used for identity verification and may result in a temporary authorization hold, normally released by the bank; the FAQ states the card is not actually charged unless the account is upgraded.
- For a standard Free Trial, if the account is not upgraded, paid trial resources are reclaimed after the grace period while Always Free resources continue. Oracle notes that some special Free Trial offers may suspend instead of continuing as Always Free.
- Oracle Always Free documentation lists 20 total HSM-protected master-key versions and 150 Always Free Vault secrets per tenancy; Private Vaults are excluded from the Always Free allocation.

### 3.2 What is not a spend control

Oracle describes Budgets as **soft limits**. Budget alerts are evaluated periodically every 24 hours. They are informational notifications, not a hard billing cap and not an automatic resource-denial mechanism. Do not create a budget and claim that it guarantees no spend.

## 4. OCI IPv6 route and egress policy

Oracle documents:
- Oracle-assigned GUA `/56` prefixes, with `/64` IPv6-enabled subnets;
- Internet routability when a GUA is assigned to a resource in a public subnet and the route table sends IPv6 traffic to an Internet Gateway;
- private subnets prohibit internet communication even when a GUA is assigned;
- the VCN Internet Resolver supports resolving external IPv6 hostnames;
- security lists and NSGs support IPv6 rules and CIDR destination prefixes.

Potential path, only after evidence and separate authorization:

`A1 VNIC (private IPv4 + GUA IPv6) → public subnet /64 → ::/0 route to Internet Gateway → exact Neon Data API AAAA destination(s)`

### 4.1 Mandatory controls

- Remove/reject SSH TCP/22 ingress from `::/0`; no public management listener or dashboard.
- Remove/reject unrestricted IPv6 egress (`::/0`, all protocols) from the worker's effective rules.
- Permit only exact verified Data API destination IPv6 CIDRs and TCP/443, plus the explicitly selected DNS resolver path.
- Do not permit a worker or untrusted agent to change NSGs, security lists, routes, DNS configuration, or IAM policy.
- If AAAA answers rotate outside the approved set, fail closed; do not broaden to all AWS/Neon/Internet IPv6 ranges.
- TLS must validate certificate chain and hostname/SNI. IP pinning without hostname validation is invalid.
- Host-level firewalling is supplemental, not the primary boundary if a compromised worker can gain root.

OCI's IPv6 default security-list examples include public SSH ingress and broad egress patterns. Never rely on defaults; inspect the effective rules. The exact account's current security lists, NSGs, public/private subnet state and route tables are unknown.

## 5. Neon endpoint, Data API and environment-variable boundary

### 5.1 Data API network exposure

- Neon returns a branch-specific HTTPS Data API URL through its Data API configuration API. The documented example uses a compute-specific `apirest` hostname, distinct from the PostgreSQL hostname.
- Neon documents IPv6 for AWS-hosted PostgreSQL endpoints. This does not establish AAAA or IPv6 HTTPS for the separate Data API proxy hostname.
- Neon explicitly documents that Data API is not protected by IP Allow and is not supported with IP Allow or Private Networking. Therefore Neon-side IP Allow / PrivateLink cannot serve as a network firewall for this route.
- Treat the Data API as publicly reachable at the network layer. Authorization must therefore be enforced by signed JWTs and narrowly scoped PostgreSQL GRANT/RLS, with the worker itself enforcing strict destination egress and TLS validation.
- The exact Data API AAAA answer, TTL, address-set stability, and IPv6-only TLS/HTTPS remain UNKNOWN. No exact endpoint URL was retrieved and no DNS or HTTP probe was run.

### 5.2 Neon Functions environment variables

Current Neon docs state that each Function deployment carries its own snapshot of user-defined environment variables. They also document `NEON_DATA_API_URL` as branch-scoped and available when Data API is provisioned on that branch. This is useful deployment behavior, but it is not a field-specific key-vault assurance.

Still not established for Function environment snapshots containing signing private keys:
- encryption and key-management boundary for the specific environment-variable storage object;
- operator/support access controls for plaintext resolution;
- snapshot retention and deletion semantics after redeploy or Function deletion;
- per-read/per-decrypt audit logging and customer-visible review path;
- isolation of build/deploy tooling and environment retrieval from arbitrary project administrators.

General statements that Neon encrypts data at rest do not by themselves prove these field-specific guarantees. **Do not store private signing keys in Neon Function environment variables until Neon provides explicit written or documented assurance for this exact data path.**
