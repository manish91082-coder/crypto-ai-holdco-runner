## 2. OCI public IPv6 path

OCI VCNs support dual-stack IPv4/IPv6. An IPv6-enabled VCN can receive an Oracle-allocated /56 Global Unicast Address (GUA) prefix. Each IPv6-enabled subnet uses a /64; a GUA prefix in a public subnet can be globally routable. OCI documents outbound- and inbound-initiated IPv6 connectivity through an Internet Gateway. A compute VNIC can receive an IPv6 address from the subnet prefix.

Possible path without assigning public IPv4 or using an IPv4 NAT gateway:
- A1 VNIC retains its required private IPv4 address.
- An existing/approved VCN has an Oracle GUA /56 and a public subnet with a /64.
- The VNIC gets a GUA IPv6 address.
- Route table sends `::/0` to the Internet Gateway.
- Worker makes an outbound TLS connection over IPv6 to the Neon Data API hostname, only if it has a working AAAA record.

OCI Service Gateway is not used for Neon. It reaches supported Oracle Services Network endpoints, not external Neon.

## 3. Neon IPv6 boundary: PostgreSQL is proven, Data API is not

Neon's official connection docs say projects provisioned on AWS support both IPv4 and IPv6 PostgreSQL addresses; Azure-provisioned projects support IPv4 only. The canonical Crypto HoldCo project is in an AWS region, so its PostgreSQL endpoint belongs to the IPv6-supported class.

The target request path is **Neon Data API over HTTPS**, not direct PostgreSQL. Neon describes Data API as a shared service implemented in its proxy fleet. Its URL is branch-specific and returned by the Data API configuration API. The reviewed official docs do not explicitly guarantee that every `apirest.*.aws.neon.tech` hostname publishes an AAAA record or accepts IPv6 HTTPS.

Therefore:
- AWS PostgreSQL IPv6 support: DOC VERIFIED.
- Data API hostname AAAA: UNKNOWN.
- Data API IPv6 TLS/HTTPS reachability: UNKNOWN.
- Direct PostgreSQL IPv6 success would not prove Data API IPv6.

## 4. Security conditions

### 4.1 Inbound deny-by-default

Oracle's IPv6 documentation describes a default security-list rule that can permit TCP/22 SSH ingress from `::/0`. This is unacceptable for a worker whose Instance Principal can sign with an HSM key.

Any future test must:
- Remove all SSH/RDP/public inbound rules, including IPv6 `::/0`.
- Expose no public management/dashboard listener.
- Ensure no SSH user inherits VM Instance Principal KMS signing authority.
- Verify NSG and subnet security-list effective ingress/egress by read-back.

### 4.2 Restrict outbound IPv6

A public IPv6 route with `::/0` egress allowed lets a compromised worker send data to arbitrary IPv6 destinations. This is not an acceptable final boundary.

Before activation:
- Resolve the exact Data API hostname's AAAA records and TTL.
- Establish whether the address set is stable and can be allowlisted in OCI egress controls.
- If it rotates, prove a bounded refresh mechanism that cannot expand to arbitrary destinations or accept DNS spoofing.
- If strict network egress cannot be enforced, do not run untrusted agent code or secrets on the VM.
- Use TLS with hostname/certificate validation. IP-only pinning without hostname validation is invalid.
- Include DNS resolver traffic explicitly in the egress policy.

Host-level nftables can supplement controls but is not a replacement for VCN/NSG egress controls if an attacker can gain root.
