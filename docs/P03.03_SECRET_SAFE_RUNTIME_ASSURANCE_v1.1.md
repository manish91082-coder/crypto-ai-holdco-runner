## 4. Proposed OCI signing architecture

### 4.1 Intended design

1. A single OCI Always Free VM runs the bounded worker. It must be created only in the tenancy's home region and only on a shape explicitly marked Always Free-eligible.
2. A narrowly matched OCI Dynamic Group identifies the one VM. A least-privilege policy grants only the key-version read and cryptographic-sign operation required for the designated key in one compartment. No tenancy-admin policy, personal API key or user API key is placed on the VM.
3. The signing key is an OCI Vault HSM-protected asymmetric RSA key (candidate: RSA-2048) with signing usage. Private key material remains inside OCI's managed HSM. The VM authenticates to OCI with Instance Principals and requests signatures through KMS.
4. `GetKeyVersion` returns the RSA/ECDSA public key in PEM format. A public-only JWKS is derived from the PEM modulus/exponent and served by a narrowly scoped, public-only Neon Function or another verified permitted endpoint. The JWKS contains no private key material.
5. The worker signs a short-lived JWT using OCI KMS with `SHA_256_RSA_PKCS1_V1_5` (the candidate mapping for JOSE `RS256`). The JWT has a fixed issuer, audience, subject and role claim (`holdco_runtime`), a short expiry (maximum 60 seconds), `iat`/`nbf`, and unique `jti`. No private key is exported to the VM.
6. Neon Data API custom-JWKS authentication validates the JWT and selects the Postgres role from the JWT `role` claim. The Data API exposes only a dedicated `holdco_api` schema containing one `SECURITY INVOKER` heartbeat RPC. The underlying `holdco` tables/views are not exposed through the Data API.
7. The heartbeat remains a bounded canary, subject to the existing daily invocation cap, kill switch, idempotency and independent read-back. No business source, agent, financial rail or production workload is enabled by this design.

### 4.2 Why RSA-SHA256 is the first algorithm to test

OCI documents RSA and ECDSA asymmetric signing. Its KMS signing interface lists `SHA_256_RSA_PKCS1_V1_5`; PostgREST documents support for `RS256` and JWKS verification. RS256 uses the standard RSA PKCS#1 v1.5 signature bytes, avoiding the DER-to-JOSE raw `R || S` conversion required by ECDSA signatures. This is a compatibility rationale, **not proof** that Neon Data API's currently deployed validator accepts this exact KMS output and key format. A disposable-branch test is mandatory.

### 4.3 Benefits over application-held signing keys

- The private signing key is never placed in source, chat, local disk, Neon environment snapshots or GitHub secrets.
- The VM uses short-lived Instance Principal identity material maintained by OCI, rather than a long-lived personal API key.
- Public key material can be published safely in JWKS; private signing remains server-side in KMS.
- One key can be rotated by publishing overlapping public JWKs with distinct `kid` values, then retiring the old key only after token TTL/cache windows have elapsed.

## 5. Free-tier and reliability facts — not a zero-cost certification

Oracle's published Always Free material currently states:

- Up to 1,500 OCPU-hours and 9,000 GB-hours per month for VM.Standard.A1.Flex, equivalent to 2 OCPUs and 12 GB memory, subject to tenancy and home-region eligibility.
- Compute must be provisioned in the tenancy's home region. Host capacity can be unavailable.
- 150 Always Free Vault secrets and 20 HSM-protected master-key versions per tenancy; private vaults are not included in Always Free.
- Up to 10 TB/month outbound data transfer is listed as Always Free.
- HSM key-version pricing material says the first 20 key versions are free; additional versions are billed. Vault API operations are documented as not separately billed by operation count.
- Instance Principal access requires a Dynamic Group and IAM policy. Oracle notes that users with SSH access to the VM can use the permissions granted to that instance.

**Reliability limitation:** Oracle may reclaim an Always Free VM when, over a 7-day period, CPU p95 is below 20%, network utilization below 20%, and (for A1) memory utilization below 20%. A low-traffic worker can therefore be reclaimed. Never generate artificial workload just to defeat reclamation. OCI Always Free does not establish guaranteed 24x7 uptime or an SLA for this mission.

**Cost/eligibility gaps:** the user's OCI account existence, home region, identity verification, account eligibility, actual A1 capacity, public IP/network path, compartment quotas, cost controls and no-overage behavior have not been verified. A published free allowance is not proof of this account's current eligibility or an automatic hard billing cap. Do not create resources until these checks are proven.

## 6. Remaining technical unknowns

1. Whether the exact Neon Data API deployment accepts an RS256 JWT signed by OCI KMS and a corresponding public-only JWKS entry; this is not established by PostgREST compatibility alone.
2. Whether the OCI HSM RSA key configuration and Sign API invocation can sign the exact JWT signing input with RS256-compatible byte semantics; this requires a proof-of-signature against the returned public key.
3. Whether `GetKeyVersion`'s PEM public key can be transformed into a correct RSA JWK (`kty`, `alg`, `use`, `kid`, `n`, `e`) and how the JWKS endpoint will be served without a new paid or Cloudflare-dependent service.
4. Whether Neon Data API enforces `iss` as well as configured `aud`, signature and time-based claims. Do not assume issuer validation without explicit docs/read-back and negative tests.
5. The exact `authenticator` role/membership behavior after Data API provisioning; no membership grant is assumed.
6. The exact injected `DATABASE_URL` database role for Neon Functions; do not assume it is least-privileged until branch-only read-back.
7. OCI home-region location versus Neon Singapore, egress routing and any data-residency implications.
8. OCI VM idle reclamation and account-side recovery/failover. No alternate free always-on runtime is approved.
9. No invoice-grade Neon Function/storage quota evidence; global governor remains paused.
10. SSH/instance access exposure: the dynamic-group grant must not become ambient authority for untrusted users or processes on the VM.
