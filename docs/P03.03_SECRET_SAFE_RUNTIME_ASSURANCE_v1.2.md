## 2. Official evidence now established

### 2.1 OCI HSM key non-exportability

Oracle's Vault documentation explicitly states that an RSA or ECDSA asymmetric master encryption key created with HSM protection stores its private key inside the HSM and does not allow export of that private key. The corresponding public key can be downloaded. Oracle documents its HSMs as FIPS 140-2 Security Level 3 certified.

This distinction matters: **the candidate uses an HSM-protected asymmetric key object, not a Vault Secret containing a private-key file.** OCI Always Free Vault secrets are a separate resource class. Oracle says secret versions are base64-encoded and encrypted by a master encryption key, but are not themselves stored within the HSM. A private-key file placed in a Secret would therefore not provide the same non-exportability property as an HSM-generated asymmetric key.

Official references:
- https://docs.oracle.com/en-us/iaas/Content/KeyManagement/Concepts/keyoverview.htm
- https://docs.oracle.com/en-us/iaas/Content/KeyManagement/Tasks/exportingkeys.htm

### 2.2 Always Free limits and constraints

Oracle's current Always Free documentation states:

- VM.Standard.A1.Flex allowance: first 1,500 OCPU-hours and 9,000 GB-hours per month, equivalent for Always Free tenancies to 2 OCPUs and 12 GB memory.
- A1 instances must be created in the tenancy's home region. The 2 OCPU total can be split across one or two A1 instances, subject to boot-volume allocation.
- 200 GB total Always Free block-volume storage is available for boot/block volumes.
- 20 total HSM-protected master-key versions and 150 Always Free Vault secrets per tenancy. Private Vaults are not included.
- First 10 TB/month of outbound data transfer is listed as free.

These are published limits, not proof that the user's tenancy exists, is eligible, has capacity remaining, has a particular home region, or is protected from all possible billed configurations.

Reference: https://docs.oracle.com/en-us/iaas/Content/FreeTier/freetier_topic-Always_Free_Resources.htm

### 2.3 Idle-instance reclamation

Oracle may reclaim idle Always Free compute instances when, over a 7-day period, all these conditions hold:

- CPU p95 utilization is below 20%.
- Network utilization is below 20%.
- Memory utilization is below 20% for A1 shapes.

A revenue worker with light or sporadic demand can meet these thresholds. Artificial traffic must never be generated solely to defeat reclamation. OCI Always Free A1 is therefore a conditional compute candidate, **not a guaranteed continuously available 24×7 runtime or uptime SLA**.

Reference: https://docs.oracle.com/en-us/iaas/Content/FreeTier/freetier_topic-Always_Free_Resources.htm

### 2.4 KMS signing algorithm maps to the RS256 construction

Oracle documents asymmetric RSA and ECDSA keys for signing and verifying data. Its KMS Sign operation accepts a base64-encoded message and includes the `SHA_256_RSA_PKCS1_V1_5` signing algorithm. The Sign API's `messageType` defaults to `RAW`, which means the service hashes and signs the original message rather than treating the input as a precomputed digest.

For a JWT, the signing input is the exact ASCII byte sequence:

`BASE64URL(protected-header) + "." + BASE64URL(payload)`

The JOSE `RS256` construction is RSA PKCS#1 v1.5 with SHA-256 over that raw signing input. OCI's documented RSA key, SHA-256/PKCS#1 v1.5 algorithm and RAW-message mode therefore form a **documented algorithm-level match**. This removes the ECDSA DER-to-JOSE signature conversion issue from the first proof-of-concept.

It is not yet an end-to-end proof: key creation settings, KMS request/response encoding, signature byte verification, public-key-to-JWK conversion, and Neon Data API acceptance still require an independently verified test.

Official references:
- https://docs.oracle.com/en-us/iaas/Content/KeyManagement/Tasks/usingkeys_topic-To_sign_data_by_using_your_Vault_master_encryption_key.htm
- https://docs.oracle.com/en-us/iaas/tools/oci-cli/latest/oci_cli_docs/cmdref/kms/crypto/signed-data/sign.html
- https://www.rfc-editor.org/rfc/rfc7518
- https://docs.postgrest.org/en/stable/references/auth.html

### 2.5 Public-key retrieval

Oracle's `GetKeyVersion` management operation returns the public key in PEM format for RSA and ECDSA keys. The proposed JWKS publisher would transform the RSA public key into public JWK members only: `kty=RSA`, `alg=RS256`, `use=sig`, `key_ops=[verify]`, unique `kid`, modulus `n`, and exponent `e`. No private key material is published.

Reference: https://docs.oracle.com/en-us/iaas/Content/KeyManagement/Tasks/usingkeys_topic-To_view_the_public_key_of_an_asymmetric_key.htm

### 2.6 Instance Principals and important inherited authority

Oracle documents that Instance Principals use certificates automatically created, assigned and rotated by OCI. A Dynamic Group selects matching instances; an IAM policy authorizes that group to use only specified resources. OCI Audit records the instance OCID as `principalId` for calls made by an instance.

Two security caveats are explicit in Oracle's documentation:

1. Any person who can access the VM (including via SSH) automatically inherits the IAM privileges granted to that instance.
2. Instance Principals are also granted `compartment_inspect`; Oracle says this permission cannot be revoked.

Thus, the proposed dynamic group must match exactly one dedicated instance, its policy must be restricted to the one designated RSA key in one compartment, and administrative/SSH access must be treated as access to the HSM signing authority. No broad tenancy policy is acceptable.

Reference: https://docs.oracle.com/en-us/iaas/Content/Identity/Tasks/callingservicesfrominstances.htm

## 3. Network route is a separate zero-cost gate

Oracle's Service Gateway provides private access only to supported Oracle Services Network services in the same OCI region, without internet traversal. Neon is an external provider, not an OCI service. A Service Gateway alone therefore does **not** prove that the worker can reach the Neon Data API.

To call Neon, the VM needs a verified route to the public Neon endpoint. Oracle documents direct internet access from a compute instance as requiring a public subnet, a public IP, an Internet Gateway, suitable route/security rules and instance-level network permission. A NAT Gateway is another possible route, but its account-specific pricing and availability must be verified before use.

Oracle lists the first 10 TB/month of outbound internet transfer as free. That allowance does not prove that the chosen public-IP/NAT/network configuration is zero-bill, nor does it create a hard no-overage guard.

The candidate network design is therefore **not selected yet**. It must be reviewed for:
- A1 subnet/public-IP eligibility and any separately billable resources.
- Internet Gateway versus NAT Gateway cost and Always Free account availability.
- Outbound-only rules to the exact Neon endpoint; no inbound SSH/public service exposure.
- DNS resolution, TLS verification, destination allowlisting and egress restrictions.
- Cross-region routing and data-residency implications between the OCI tenancy home region and Neon `aws-ap-southeast-1`.
- A true no-paid-upgrade/no-overage account posture.

Official references:
- https://docs.oracle.com/en-us/iaas/Content/Network/Tasks/servicegateway.htm
- https://docs.oracle.com/en-us/iaas/Content/Network/Concepts/overview.htm

## 4. Neon authentication compatibility boundary

Neon Data API documentation confirms that the JWT `role` claim selects the Postgres role, and `sub` identifies the subject. A custom role must exist, be granted to the Data API's `authenticator` role, and possess only the privileges required by the request. The proposed token is fixed to `role=holdco_runtime`, one fixed subject, a fixed issuer/audience, a maximum 60-second expiry, and a unique `jti`.

The upstream PostgREST documentation describes RS256 and JWKS verification, but that is a compatibility reference, not a live proof for this specific Neon Data API configuration. Neon-specific `iss` enforcement is also not established by the public material reviewed. A disposable-branch test remains mandatory for:
- RS256 acceptance and public JWKS key matching.
- Exact issuer, audience, expiry and not-before validation.
- Custom role claim and authenticator membership.
- Denial of raw `holdco` table/view access.
- One `SECURITY INVOKER` RPC in `holdco_api` only.
- Bad signature, wrong/missing role, expired/future token, wrong audience/issuer, unknown `kid`, malformed JWKS, anonymous caller and role-escalation attempts.

Neon Managed Better Auth's OAuth provider is rejected for unattended M2M bootstrap: its official documentation says no `client_credentials` grant exists and access tokens are always issued on behalf of a signed-in user.

Neon Function environment snapshots remain unapproved for the private signing key: every deployment carries a snapshot of user-defined variables, but the reviewed function-specific docs do not establish all required encryption, provider/operator-access, old-snapshot retention/deletion, log exposure and audit guarantees.

Official Neon references:
- https://neon.com/docs/data-api/custom-authentication-providers
- https://neon.com/docs/data-api/access-control
- https://neon.com/docs/auth/guides/plugins/oauth-provider
- https://neon.com/docs/compute/functions/environment-variables

## 5. Proposed architecture — conditional, not deployed

1. One OCI Always Free A1 VM in the tenancy's home region, only if the exact tenancy and account quotas prove eligible.
2. One HSM-protected asymmetric RSA key in a standard eligible Vault (not a paid Private Vault). The private key is generated and retained inside the HSM.
3. One exact-instance Dynamic Group and a least-privilege policy permitting KMS signing with only that key. No user API key, local private-key file or broad tenancy policy.
4. The worker creates the fixed JWT signing input and asks KMS to sign the raw input using `SHA_256_RSA_PKCS1_V1_5`. It verifies the resulting signature against the KMS public key before any network call.
5. A public-only JWKS endpoint serves the public key and `kid`. A Neon Function could be evaluated as a static public JWKS publisher, but only after its quota, domain/provider path, Cloudflare exclusion and deployment scope are verified.
6. Neon Data API branch-only validation exposes only `holdco_api` and one `SECURITY INVOKER` heartbeat RPC. The underlying `holdco` tables/views are not exposed.
7. The heartbeat is bounded by a daily cap, idempotency, a kill switch and an independent read-back. No opportunity source, agent, payment rail or production workload is activated by this architecture.

## 8. Bounded validation plan — not an authorization

No OCI resource or Neon test branch may be created until all account, region, free-quota, network route, cost and policy preconditions are proven and a separate bounded authorization is recorded.

If authorized later:
1. Validate one eligible A1 VM and one HSM RSA key version only.
2. Create the exact-instance Dynamic Group and least-privilege KMS policy; confirm no user API key is on the VM and inspect OCI Audit principal attribution.
3. Verify the HSM key cannot be exported and that the public key can be retrieved.
4. Sign a non-secret fixed test string first, using KMS RAW + SHA_256_RSA_PKCS1_V1_5; independently verify the signature using the public key.
5. Test the exact JWT signing input and RS256 signature; publish only public JWK material.
6. Obtain separate approval for one short-lived Neon child branch. Test the full positive/negative JWT and database permission matrix.
7. Exercise kill switch, daily ceiling, idempotency, key rotation overlap and cleanup; delete test-only resources only within the approved cleanup scope and verify read-back.
8. Do not promote to main, enable recurring triggers, or activate agents, opportunities or financial rails by implication.
