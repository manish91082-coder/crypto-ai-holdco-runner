## 2. Neon SDK source inspection
Public source was read through the connected GitHub repository:
- neondatabase/neon-pkgs, packages/sdk/src/neon/resources/role-access.ts, blob b84476875f279c1a7221035c47ebc07fd1459af1.
- neondatabase/neon-pkgs, packages/sdk/src/neon/resources/roles.ts, blob b9c7d9785ba6f2debde48b6ca206349e2e5e107a.

Source links:
- https://github.com/neondatabase/neon-pkgs/blob/main/packages/sdk/src/neon/resources/role-access.ts
- https://github.com/neondatabase/neon-pkgs/blob/main/packages/sdk/src/neon/resources/roles.ts

Code-level findings:
1. role-access.ts explicitly states that the API refuses to reset the password of a role that has none.
2. For a **new** scoped read_only/read_write role, the SDK connects as the database owner, creates the role as NOLOGIN with a generated bootstrap password in a literal SQL statement, grants privileges, asks Neon to reset the password through the control plane, and enables LOGIN only after reset succeeds.
3. The same source explicitly warns that statement logging may record the bootstrap password.
4. This is a create-new-role path, not an initializer for the existing holdco_runtime identity. Creating a replacement would change role identity and require exact ACL, ownership, default-privilege and membership migration; the SDK's coarse scoped-role template does not reproduce this project's custom per-object/per-column allowlist automatically.
5. The SDK's noLogin=true path deliberately creates the role with no password and returns before password reset. It does not solve first-password initialization.
6. The SDK's default/admin role path joins neon_superuser, which violates the locked least-privilege requirement.

Decision: the SDK is informative for a new role lifecycle but is not an admissible solution for the existing role. It must not be used to create a parallel/replacement role under the current mission authority.
