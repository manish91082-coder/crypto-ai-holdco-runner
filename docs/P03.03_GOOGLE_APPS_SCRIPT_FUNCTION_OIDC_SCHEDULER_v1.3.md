## 1. Architecture
A thin owner-created Google Apps Script time-driven trigger obtains the effective user's OIDC identity token with explicit openid scope and sends it over HTTPS to the existing isolated Neon Function route:
POST /internal/google/scheduler/dispatch

The Function verifies Google's RS256 signature using the published JWKS, exact accepted issuer, exact OAuth client audience, SHA-256 hash of the effective user's sub, and fresh token time claims. It uses existing Neon-managed database identity crypto_holdco_function. It does not use Neon Data API and does not create a PostgreSQL role, password, membership or grant.

Neon Data API is rejected for this mission because its PostgreSQL execution role is selected from the JWT role claim; a token without role falls back to anonymous. A custom role claim would require an existing role and authenticator membership. Data API remains disabled on main and pilot. Official access-control source: https://neon.com/docs/data-api/access-control.

## 3. Replay/idempotency guard
Source-only migration: db/migrations/pilot/20261128_google_scheduler_replay_guard.sql.
Source-only SQL regression: db/tests/pilot/verify_google_scheduler_replay_guard.sql.
- Proposed table uses tick_id UUID primary key and token_hash unique.
- The SECURITY DEFINER routine is designed for crypto_holdco_function EXECUTE only; no direct replay-table access.
- Duplicate tick or duplicate verified bearer hash returns HTTP 409.
- Markers retain through token expiry plus 24 hours.
- Semantics are at-most-once admission, not exactly-once processing.

If Google returns a still-valid identical token for two ticks, the second would be denied as replay.

## 4. Official platform constraints reviewed
- ScriptApp.getIdentityToken returns the effective user's OpenID Connect token only when openid is explicitly granted in appsscript.json; it is not among default scopes. The script project's OAuth client ID is the expected audience to pin. Sources: https://developers.google.com/apps-script/reference/script/script-app#getIdentityToken and https://developers.google.com/apps-script/guides/services/cloud-run.
- Installable triggers execute under the account that created them. Time-driven trigger timing may be slightly randomized. Source: https://developers.google.com/apps-script/guides/triggers/installable.
- Current published quota table lists 90 trigger-runtime minutes/day and 20,000 URL Fetch calls/day for consumer accounts; Workspace baseline 6 hours/day and 100,000 calls/day. Limits are per user, reset 24 hours after first request, and may change. Source: https://developers.google.com/apps-script/guides/services/quotas.
- These published limits do not prove this owner's account type, remaining quota, or account-specific service entitlement.
