## 1. Decision
**NO-GO for immediate owner API token rotation.** The current owner credential remains enabled and has not expired. Its external/manual consumer set is not proven complete, and no protected one-time secret-delivery path is verified. A replacement must not be issued until its consumer cutover can be validated end-to-end.

This is an availability and secret-handling control, not a refusal to complete lifecycle work. Do not revoke the existing token merely because CI no longer needs it.

## 4. Safe rotation protocol (not yet executed)
1. **Consumer census:** enumerate every live/manual consumer of owner-operator-pilot, record environment/owner/scope and confirm how its secret is updated. Do not collect raw values in chat, SQL or the repository.
2. **Issue a new application token:** use an approved server-side minting path backed by a cryptographically secure random generator (at least 32 random bytes). Store only its SHA-256 hash, subject, minimal explicit scope set, expiry, rotation group and audit metadata. Never place plaintext token in a SQL literal or query log.
3. **Protected delivery:** expose the raw value exactly once through a user-approved secret manager or another verified private one-time delivery channel. Do not place it in public GitHub, workflow logs, Neon evidence excerpts, chat, README, issue comments or a shared dashboard.
4. **Overlap and verify:** keep old and new tokens valid during a short cutover window. From the actual consuming client, prove one positive authorized HTTP request, one wrong-scope denial (401), and one unauthenticated denial (401). Confirm the new row's last_used_at changes.
5. **Consumer cutover:** update every inventoried consumer and verify healthy operation. CI should continue using OIDC, not the long-lived application token.
6. **Revoke old token:** only after all consumers confirm the new credential, revoke the old token and read back enabled=false / revoked_at IS NOT NULL without selecting token_hash.
7. **Post-rotation audit:** record metadata only (subject, scopes, created/expiry/revocation, validation timestamp, evidence IDs). Do not preserve or log plaintext values.

If the new-token issuance response is lost, do not retry a non-idempotent rotation blindly. Create a separate replacement under a new identifier, verify it, then revoke the abandoned credential by metadata. Never let a failed delivery silently invalidate the only working token.

## 5. Release and safety controls
- Do not use Neon create_credential / rotate_credential provider-scoped tokens as application API tokens; their scope/type is different.
- Do not grant the OIDC identity any scope beyond metrics:read.
- Do not create APP_API_TOKEN or a Railway service to make this runbook appear complete.
- Keep Neon trigger disabled and Governor PAUSE_DEGRADED / work_allowed=false.
- Keep scheduler, worker dispatch, external submissions, wallet signing, trading, transfers and payments disabled.
- No token was created, rotated, reissued or revoked by this v1.0 runbook publication.

## 6. Closure criteria
This sub-gate closes only after:
- consumer census is signed off;
- one-time protected delivery is demonstrated;
- the replacement application token passes positive and negative HTTP tests;
- all intended consumers confirm cutover;
- old token revocation is provider-read-back verified;
- token raw values/hashes are absent from logs, repo, chat and audit evidence.

P03.03 remains PARTIAL until its full WBS gate, including remaining provider/runtime assurance, passes. P03.05 remains PLANNED / NOT ACTIVE.
